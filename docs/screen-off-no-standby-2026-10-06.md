# Вимкнення екранів без Modern Standby — 2026-10-06

На реальному ASUS TUF Gaming F15 FX507ZC4 встановлений і запущений оновлений Windows-агент. Android APK не змінювався: існуючі endpoint та формат відповідей збережені.

## Причина та виправлення

`powercfg /a` показує S0 Low Power Idle з відключенням мережі. Журнал Kernel-Power містив події 506 з причинами `SC_MONITORPOWER`, `Idle Timeout` та `Lid`. Пробний цикл зі старою командою також породив події Modern Standby; його не зараховано як доказ усунення проблеми.

- Команда вимкнення екранів більше не надсилає `SC_MONITORPOWER`. Windows зберігає дисплей логічно активним; власне чорне вікно закриває весь віртуальний робочий стіл, яскравість внутрішнього LCD знижується до 0, зовнішні монітори за підтримки використовують DDC/CI.
- Перед затемненням встановлюються запити SYSTEM, EXECUTION та DISPLAY. Windows API перевіряються; відмова не показується як успішний захист. Запити SYSTEM/EXECUTION тримаються з запуску агента й після відновлення екранів.
- На увімкнення чорне вікно ховається, повертається попередня яскравість LCD, надсилається DDC-команда увімкнення зовнішніх моніторів. Локальний вихід із чорного екрана — Escape або Alt-F4; рухи та натискання миші його випадково не знімають.
- Окрема команда гібернації залишається доступною й знімає захисні запити перед виконанням.
- Активний збалансований план: автоматичний сон та гібернація — Never, закриття кришки — Do nothing, для AC і DC. Попередні шість значень збережені. Критичні дії батареї, BIOS та режим підтримуваних станів Windows не змінювались; перезавантаження не потрібне.

Запити DISPLAY та SYSTEM мають використовуватися разом; SYSTEM/EXECUTION впливають на доступність процесу при керуванні живленням. Це відповідає [контракту PowerSetRequest Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest).

## Фактична перевірка

На живому ASUS, від мережі AC, у фізичній console-сесії 6:

- `go test ./...`: 21 тест, включно з відмовами PowerCreateRequest/PowerSetRequest, очищенням частково взятих запитів і відмовою гасити екран без захисту. `go vet ./...`: без помилок. Windows-бінарник зібраний і встановлений.
- Запит screen-off успішний за 0,61 с; WMI readback яскравості LCD — 0.
- 45 секунд без опитування API: після паузи `monitor_sleeping=true`, `keep_awake_active=true`, агент ASUS доступний.
- Wake успішний за 0,49 с; `monitor_sleeping=false`; яскравість LCD повернулась до попередніх 86%.
- За весь контрольний цикл відсутні Kernel-Power 42/506, тобто журнал не зафіксував входу в сон/Modern Standby.
- Конфігурація агента та токен не змінені, попередній виконуваний файл має резервну копію.

Внутрішній екран тепер затемнюється та показує чорне зображення, а не переводиться в системний режим вимкнення дисплея. Це залишає Windows активною. Значення 0 означає мінімальну підтримувану яскравість панелі, а не виміряне нульове споживання. Фізичне вимкнення підсвітки зовнішнього монітора, тривалий тест на батареї, закриття кришки й керування з фізичного телефону в цьому проході не перевірялися.

Дані останнього циклу: `ASUS-screen-cycle-2026-10-06.json`. Попередні значення плану: `ASUS-power-settings-before-2026-10-06.json`. Для відновлення тільки налаштувань Windows використовується `Restore-ASUS-power-settings.ps1` поруч із JSON; агент, поки працює, продовжує тримати свої запити віддаленої доступності.
